| 启动握手恢复 | MCU先启动、模拟器后连接时一次性`page`命令会丢失 | 增加刷新帧`A5 01 02 5A`，重新加载dashboard并上报ID | 首次联机失败可显式恢复 |
| 定点文本格式化 | 嵌入式C库不一定支持浮点`printf`，数字曾为空 | 浮点值先转定点整数，再用`%lu`输出 | 不依赖`_printf_float`也能稳定显示 |

## 3. 现场运行时故障及修复

初版虽然能编译，但现场依次暴露了三个独立问题。只看“屏幕空白”无法区分，
必须用ST-Link读取CPU和外设现场。

### 3.1 进入`main()`前触发半主机HardFault

#### 现象

- 上电后屏幕无图；
- 四个按钮有HMI侧发送帧，但MCU无响应；
- ST-Link读取PC发现CPU停在`HardFault_Handler`。

#### 诊断证据

- 异常栈原始PC为`0x0800180C`；
- 对应机器码包含`AB BE`，即`BKPT 0xAB`；
- Map文件显示该地址属于Arm运行库`_sys_command_string`；
- 说明运行库在进入`main()`前尝试通过半主机获取`argc/argv`。

#### 根因

队友历史构建使用ArmClang 6.23，会自动带出`__ARM_use_no_argv`；当前本机
ArmClang 6.7重新构建后没有该标记，运行库选择了半主机命令行路径。脱离调试
宿主运行时，`BKPT 0xAB`升级为HardFault。

#### 修复

在`main.c`的CubeMX用户变量区显式保留：

```c
#if defined(__ARMCC_VERSION)
__attribute__((used)) int __ARM_use_no_argv;
#endif
```

#### 预期效果

启动库不再查询半主机命令行，MCU可正常进入`main()`。修复后Map文件不再把
`_sys_command_string`链接进最终运行路径。

### 3.2 2048点计算饿死UART轮询接收

#### 现象

- CPU已离开HardFault；
- HMI按键发出了`A5 01 01 5A`等帧，但MCU只收到首字节；
- 页面初始化和四个按钮仍表现为无反应。

#### 诊断证据

- RAM中的HMI解析器停在第一个`0xA5`；
- USART3 `ISR`出现ORE；
- `RDR`中仍残留`0xA5`；
- 主循环正在执行2048点FFT、排序和测量，无法足够及时地轮询4字节帧。

#### 根因

115200 bit/s下一个字节间隔约86.8微秒。主循环长时间计算时未读取USART3，
后续字节覆盖接收寄存器并产生Overrun Error。HAL轮询接收路径没有可靠恢复，
于是后续按钮永久失效。

#### 修复

- `Display_Init()`先清ORE和RDR，再启动`HAL_UART_Receive_IT()`；
- `HAL_UART_RxCpltCallback()`每收到一个字节立即喂给原帧解析器，并重新挂接；
- `HAL_UART_ErrorCallback()`清ORE、丢弃残缺帧并恢复接收；
- FE/FD也由同一中断解析为`s_last_hmi_status`；
- 曲线生成与批量发送仍留在主循环。

#### 预期效果

FFT长任务不再导致短按钮帧丢失；即使现场出现一次ORE，UART也能自动恢复，
而不是永久失去响应。

### 3.3 `AnalyzerResult`局部变量导致1 KB主栈溢出

#### 现象

- UART中断接收修复后，页面可以开始初始化，但随后再次HardFault；
- PC最终停在`HAL_UART_Transmit()`附近，看起来像UART发送故障。

#### 诊断证据

- `CFSR=0x00008200`：精确BusFault且BFAR有效；
- `HFSR=0x40000000`：可配置Fault被强制升级；
- 异常栈原始PC位于`HAL_UART_Transmit()`；
- 被访问地址`BFAR=0xBE828504`明显不是合法RAM或外设地址；
- 运行时UART句柄指针已经损坏；
- 当时MSP为`0x2000A9F8`，低于旧Map中的主栈底`0x2000B050`；
- `AnalyzerResult`实际大小1084字节，单个就超过启动文件的1024字节主栈；
- `Display_Task()`和`Display_DrawDashboard()`曾嵌套保存两份局部快照。

#### 根因

大结构体局部变量覆盖了栈外静态数据，其中包括`s_uart`。UART函数只是最先
解引用坏指针的位置，并不是最初的破坏者。

#### 修复

- `display.c`增加模块级静态`s_display_result`；
- `analyzer_bridge.c`增加模块级静态`s_publish_result`；
- `Display_Task()`、`Display_DrawDashboard()`和
  `AnalyzerBridge_PublishReal()`不再创建大号局部快照；
- 不改CubeMX启动文件和栈配置，避免掩盖真实内存设计问题。

#### 预期效果

大对象进入ZI静态RAM，函数栈只保留少量标量、指针和HAL调用帧。最终Map中：

```text
s_display_result = 1084 bytes，静态RAM
s_publish_result = 1084 bytes，静态RAM
Stack_Mem         = 1024 bytes
```

## 4. 使用ST-Link判断问题的方法

本轮采用“先定CPU状态，再定原始故障位置，最后关联Map和源码”的顺序。

### 4.1 先确认板卡身份

```powershell
STM32_Programmer_CLI.exe -c port=SWD mode=UR reset=HWrst
```

确认：

```text
目标电压
ST-Link固件
Device ID
芯片型号
Flash容量
```

### 4.2 冻结并读取核心寄存器

```powershell
STM32_Programmer_CLI.exe `
  -c port=SWD mode=HotPlug `
  -halt `
  -coreReg PC LR MSP XPSR
```

判断：

- `XPSR`低9位是否处于异常号3（HardFault）；
- `PC`是否落在`HardFault_Handler`；
- `MSP`是否位于Map给出的合法栈区。

### 4.3 读取Fault寄存器

```powershell
STM32_Programmer_CLI.exe `
  -c port=SWD mode=HotPlug `
  -r32 0xE000ED28 0x18
```

重点读取：

```text
CFSR  0xE000ED28
HFSR  0xE000ED2C
DFSR  0xE000ED30
MMFAR 0xE000ED34
BFAR  0xE000ED38
```

### 4.4 回读异常栈帧

异常时根据MSP/PSP读取8个压栈字：

```text
r0 r1 r2 r3 r12 lr pc xPSR
```

这里的压栈`pc`才是进入HardFault前的真实故障指令。再用`.map`、反汇编和机器
码定位其所属函数。

### 4.5 读取外设和模块状态

当CPU没有Fault但功能无响应时，继续读：

- USART3 `ISR/RDR/CR1`，检查ORE、RXNE、RX中断使能；
- HMI解析器索引，判断收到0、1还是完整帧；
- `s_dashboard`，判断曲线ID和`valid`；
- `s_visible_periods`、`s_pending_action`和结果`sequence`。

这种方法可以区分：

```text
HMI根本没发
→ MCU没收到
→ 收到但解析失败
→ 解析成功但页面未ready
→ 绘图发送失败
→ CPU已经异常
```

不要把所有“屏幕无图”都归因于HMI工程或曲线ID。

## 7. 冻结规则

本次发布后：

1. `firmware`成为后续融合微调的唯一基线；
2. 不回写`teammate_adc_newest`或`tjc_display_demo`；
3. 后续优先改测量标定、算法边界和真实信号，不再重构已稳定HMI主链；
4. 若出现屏幕无图，先按本文ST-Link阶梯检查CPU、Fault、栈、UART和页面状态；
5. 任何会增加大局部数组或结构体的改动，必须重新检查Map和主栈；
6. 编译成功不等于运行成功，必须保留“Clean Build → 烧录校验 → HMI回归 →
   ST-Link运行态检查”的闭环。
